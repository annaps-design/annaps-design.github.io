01. Purchase Orders — автоматизация

Было

Устаревший дизайн формы для просмотра и редактирования, плотные экраны с данными, ручной ввод и согласование каждого PO.

Стало

Разделённые режимы Read/Edit, автозаполнение из загруженного документа, авто-утверждение по правилам.

Контекст

Purchase Orders — создание, хранение и обработка заказов на покупку. Секция росла вместе с продуктом и к моменту старта не соответствовала обновлённой дизайн-системе. Типовой PO проходил тот же длинный путь согласований, что и нестандартный.

Проблемы пользователей

Флоу создания перегружен. Много шагов, смешанные режимы просмотра и редактирования, плотные формы, которые тяжело читать.

Layout не системный. Формы и таблица списка жили по своим правилам — интерфейс переставал быть предсказуемым.

Нет автоматизации. Ручной ввод и лишние шаги даже там, где данные повторяются от заказа к заказу.

Гипотезы

Разделим Read и Edit и унифицируем layout форм, приведем их к паттерну системы — вырастут читабельность и скорость работы.

Автоматизируем заполнение и утверждение в повторяющихся сценариях — станет меньше ручных действий и ошибок.

Решение

Разделение Read и Edit

Режим просмотра отвечает за чтение: плотность, иерархия, сканируемость. Режим редактирования — за ввод. Layout форм приведён к системным паттернам продукта.

Таблица списка PO

Пересобрала иерархию строки, читабельность и поиск нужного заказа.

Автозаполнение из документа

Пользователь загружает документ — система разбирает его и заполняет форму, пользователь проверяет и правит перед отправкой. Прописала ограничения, системные подсказки и поведение при неполном распознавании.

Правила авто-утверждения

Интерфейс создания и управления правилами: при выполнении заданных условий новый PO утверждается без участия человека. Проработала уведомления и статусы.

Результат

  • Меньше когнитивной нагрузки в работе с PO: чтение и ввод больше не смешаны
  • Типовые заказы проходят без ручных шагов
  • Секция приведена к дизайн-системе и продуктовым паттернам
  • Проработаны сценарии, статусы, ограничения, состояния системы, уведомления и системные подсказки.

02. Places — добавление локаций

Было

Адрес заполнялся вручную, координаты и таймзона — отдельными действиями, расписание — по одному дню на каждый из семи, на ноутбуках проблема с загрузкой шаблона, не хватает полей для большего понимания контекста локации.

Стало

Адрес вводится в одно поле с подсказками, остальное система подставляет сама, соответствует дизайн-системе, responsive-версия, новые поля

Контекст

Places — секция для добавления и управления локациями. Импорт через шаблон существовал, но упирался в технические ограничения, поэтому заметная часть локаций всё равно заводилась руками через интерфейс.

Боли пользователей

Провела UX-аудит секции: Hotjar-записи, интервью с пользователями и стейкхолдерами. Пять проблем.

Адрес заполнялся вручную. Все поля — руками, координаты и таймзона — отдельными действиями. Отсюда ошибки ввода, долгое time on task.

Расписание задавалось по одному дню. Стандартный график «пн–пт, 9:00–18:00» — семь одинаковых заполнений.

Сотрудников искали скроллом. Ни поиска, ни фильтра по роли: нужно было помнить, кто есть кто, и листать список.

Импорт ломался на ноутбуках. Флоу перегружен, а на 13” кнопки основных действий уходили за пределы вьюпорта.

Недостающие поля в системе. Пользователи просили добавить поля, чтобы синхронизировать данные, которые хранились в отдельных табличках для проекта.

Гипотеза

Если система подставит большую часть обязательных полей сама при выборе адреса, создание локации ускорится, а ошибок ввода станет меньше.

Решение

Автозаполнение адреса

Поиск с подсказками по мере ввода. При выборе адреса подставляются страна, город, индекс и метка на карте.

Сценарии помимо счастливого пути
  • Совпадений нет → полный ручной ввод
  • Пользователь правит автозаполненные данные
  • Введённое конфликтует с найденным
  • Повторное авто-добавление того же адреса в форме

Групповое расписание

Одно время работы задаётся сразу на несколько выбранных дней. Отдельно проработала дни с другим графиком и круглосуточный режим.

Поиск сотрудников по имени и роли

Переработала добавление и удаление людей в локации. Учла случай, когда сотрудник уже не в компании.

Импорт через шаблон

Упростила флоу, добавила системные уведомления о статусе загрузки, переписала инструкцию, починила сетку — действия больше не прячутся на ноутбуках.

Новые поля в форме

Разобралась, какие поля в каком контексте используется и в какую табу формы необходимо добавить.

Результат

  • Создание локации свелось к вводу адреса и проверке подставленного вместо заполнения 5 полей
  • Флоу стал предсказуемым для новых пользователей
  • Секция переведена на дизайн-систему и готова к дальнейшим доработкам
  • Появилась responsive-версия
  • Добавлены новые поля и платформа теперь источник информации, а не разрозненные таблички
Что дальше. Гипотезы, которые не реализовали из-за технических ограничений:
  • Картографический API с более актуальными данными
  • Ускорение backend-загрузки секции и импорта через шаблон
  • AI-проверка данных перед сохранением

03. Filters & Dropdowns — Design alignment

Было

Фильтры на ~20 страницах (+мобильные), выросших фрагментарно, — разный вид, разное поведение.

Стало

Библиотека reusable-компонентов с едиными правилами, desktop и responsive.

Моя роль
  • Product Designer
  • Design System
Участие в процессе
  • Design Process Owner

Проблема

Продукт развивался долго, фильтры и dropdown’ы добавлялись под конкретные задачи и разными командами. Итог: одинаковые по смыслу элементы выглядят и ведут себя по-разному. Пользователь каждый раз переучивается, поддержка дорожает, каждый новый фильтр проектируется с нуля.

Как шла работа

Аудит. Собрала все фильтры в системе, разложила по типам, сложности и сценариям использования, выписала несоответствия и повторяющиеся паттерны.

Система. Сформулировала UX-принципы и требования, спроектировала унифицированные компоненты под desktop и responsive, написала дизайн-спецификацию.

Внедрение. Показала применение обновлённых фильтров на реальных страницах продукта, провела hand-off, сопровождала реализацию, сделала Design QA.

Результат

  • Reusable-компоненты фильтров в системе
  • Одна структура, одно поведение, один визуальный стиль
  • Новый фильтр собирается из готового, а не проектируется заново
  • Стоимость внедрения и поддержки снизилась

04. Colour Variables

Было

Набор цветов (стили), накопленный за годы, — часть используется как значения, часть как смыслы.

Стало

Трёхуровневая система токенов и миграция легаси без единого визуального изменения.

Моя роль
  • Design System
  • Product Designer
Участие в проекте
  • Инициировала и вела проект

Проблема

Цвета добавлялись постепенно под разные задачи и команды. Часть жила как конкретные значения, часть — как семантические сущности, похожие оттенки применялись непоследовательно. Любое расширение — новое состояние, компонент, тема — превращалось в ручной перебор.

Решение

Провела аудит всех цветовых значений и сгруппировала их по назначению. Спроектировала иерархию:

Primitive — базовая палитра, сырые значения

Semantic — цвет по смыслу: текст, фон, границы, статусы

Component — привязка к конкретным компонентам

Отдельная часть работы — маппинг легаси-цветов на новые токены так, чтобы в интерфейсе визуально ничего не поменялось. Плюс правила нейминга, использования и миграции, обновлённая документация дизайн-системы и обновлённые компоненты.

Результат

  • Цвета стали семантическими, консистентными и управляемыми
  • Меньше дублей и визуальных расхождений
  • Новые состояния и темы добавляются без ручного перебора
  • Есть устойчивая основа для дальнейшей эволюции визуального языка

05. Empty states — Design alignment

Было

Разрозненные экраны без данных — свои тексты, иллюстрации, тон.

Стало

Одна структура, набор иллюстраций, шаблоны текстов и документация.

Моя роль
  • Design System
  • Product Designer
Задача
  • Редизайн в рамках развития SDC

Проблема

За время развития SDC накопились не связанные между собой пустые состояния: разный тон, разный визуальный стиль, разная структура. Продукт выглядел собранным из кусков, а пользователю было неочевидно, что делать дальше.

Как шла работа

Аудит. Собрала все существующие empty states, разложила по типам — нет данных, ошибка, фильтр без результата и т.д. Сравнила тексты, тон коммуникации, визуал, структуру и иерархию элементов.

Система. Определила единый формат: заголовок → поясняющий текст → CTA (когда он уместен) → иллюстрация. Сделала шаблоны компонентов, набор иллюстраций в одном стиле и шаблоны текстов — понятных и нейтральных, с запасом гибкости под разные сценарии.

Внедрение. Прошла по всем страницам платформы, обновила экраны под новую систему, подготовила подробную спецификацию для разработки.

Результат

  • Выросла визуальная консистентность продукта
  • Понятнее, что делать, когда данных нет
  • Новая страница получает empty state из готового паттерна, а не собирает с нуля
